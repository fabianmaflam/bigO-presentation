The formal definition: eventually below a constant multiple

f(n) = O(g(n))  ⟺  ∃C > 0  ∃n0  ∀n ≥ n0 : |f(n)| ≤ C·|g(n)|

∃C > 0
There is some fixed multiple of g. Constant factors don't matter.
∃n0
There is some starting point. Small inputs don't matter.
∀n ≥ n0
From that point on, with no exceptions.
|f| ≤ C·|g|
f never exceeds that multiple of g.

In words

From some point on, f grows no faster than g, up to a constant factor.

The pair (C, n0) is called the witnesses. To prove a Big O claim, you exhibit them.

Big O is an upper bound: n = O(n²) is true, just not tight. The notation goes back to Bachmann (1894); Knuth brought it into computer science in 1976.

This is the formal definition. f of n is Big O of g of n if there exist a positive constant C and a threshold n₀ such that, for every n ≥ n₀, |f(n)| is at most C times |g(n)|.

Read the quantifiers left to right, like in our predicate-logic unit: there exists C, there exists n₀, for all n ≥ n₀.

Each piece has a job. C lets us ignore constant factors. n₀ lets us ignore small inputs: the inequality only has to hold eventually. And "for all n" means no exceptions after that point.

C and n₀ are called witnesses: to prove a Big O claim, you show them. And Big O is an upper bound: "n is O(n²)" is true, just not tight.

Proving n² is not O(n): negate the quantifiers

¬( ∃C ∃n0 ∀n ≥ n0 : n² ≤ C·n )

≡  ∀C ∀n0 ∃n ≥ n0 : n² > C·n

Negation turns every ∃ into ∀ and every ∀ into ∃, and flips ≤ into >. Same rule as in our predicate-logic unit.

Proof

Take any C > 0 and any n0.
Choose n = max(n0, ⌊C⌋ + 1).
Then n ≥ n0 and n > C,
so n² = n·n > C·n.
No choice of witnesses survives. ∎

How do we prove that something is NOT Big O? We negate the definition.

Negating "there exists, there exists, for all" gives "for all, for all, there exists", and ≤ becomes >. So to show n² is not O(n), we show: for every C and every n₀, there's some n ≥ n₀ that breaks the inequality.

Take any C and n₀. Choose n bigger than both. Then n > C, so n² = n·n > C·n. The inequality fails, and since C and n₀ were arbitrary, no witnesses exist.

Why the limit proves Big O

If f/g → L < ∞, then eventually f/g < L + 1. So C = L + 1 is a witness.

The project requires calculus, and this is where it comes in. Instead of hunting for witnesses, we look at the ratio f over g as n goes to infinity.

If the limit is a finite number L, then eventually f/g is less than L + 1, so C = L + 1 is a witness and f is O(g). If the limit is 0, f grows strictly slower. If it's infinity, f is not O(g).

Our polynomial over n² tends to 3: same growth. Log n over n: by L'Hôpital, (1/n)/1 tends to 0, so log n grows slower. n² over n is just n, which goes to infinity. And n³ over 2ⁿ tends to 0: any polynomial loses to an exponential.

This is the relation between two functions going to infinity: their ratio tells us who wins.

Why is Big O the right tool for algorithms? Running time is the number of steps times the time per step.

First: the time per step depends on the processor, the language, the compiler. But it's a constant, and Big O absorbs constants into C. So the classification doesn't depend on the machine.

Second: the hard case is large inputs, which is exactly the limit n → ∞. Third: it composes. Steps in sequence add, so we keep the biggest term; nested loops multiply.

Counting comparisons: why some sorts are n² and others n log n

Selection sort (bubble sort is similar)

Find the smallest of n, then of the remaining n − 1, and so on. Each square below is one comparison (n = 8).

(n−1) + (n−2) + … + 1 = n(n−1)2 = ½n² − ½n = Θ(n²)

Merge sort

Halve until size 1 (8 → 4 → 2 → 1 is log28 = 3 halvings), then merge back. Merging a whole level costs at most n comparisons.

T(n) = 2T(n/2) + n  ⇒  n per level × log2n levels = Θ(n log n)

Now let's analyse sorting. We count comparisons, because comparing two elements is the basic step.

Selection sort scans the whole list to find the smallest element, then scans the remaining n − 1, and so on. That's (n−1) + (n−2) + … + 1 comparisons, which equals n(n−1)/2: this triangle, about half of the n-by-n square. Half a square is still quadratic: ½n² − ½n is Θ(n²). Bubble sort and insertion sort have the same worst case.

Merge sort is different. It splits the list in half, again and again, until pieces have size 1: that takes log₂ n levels. Then it merges, and merging one whole level costs at most n comparisons. n per level times log₂ n levels: n log n. As a recurrence: T(n) = 2T(n/2) + n.

The floor no comparison sort can break

A sort that only compares elements must tell apart all n! possible orders. Each comparison has two outcomes, so it needs at least log2(n!) comparisons, and log2(n!) grows like n log2 n.

worst case = Ω(n log n)

So merge sort and heapsort are asymptotically optimal. Quicksort is still popular: with a random pivot its expected time is n log n and its constants are small.

To summarise: bubble, insertion and selection sort are quadratic in the average and worst case. Merge sort and heapsort are n log n always. Quicksort is n log n on average but n² in the worst case.

And here's the deeper result: no algorithm that sorts only by comparing elements can beat n log n in the worst case. It has to tell apart all n! possible orders; each comparison has two outcomes, so it needs at least log₂(n!) comparisons, and log₂(n!) grows like n log n.

So merge sort and heapsort are asymptotically optimal.

What to remember

Definition. f = O(g) means ∃C ∃n0 ∀n ≥ n0 : |f(n)| ≤ C·|g(n)|: below a constant multiple, eventually.

Asymptotic. It keeps only the shape of growth as n → ∞, and the limit of f/g tells us who wins.

Algorithms. It ignores exactly what depends on the machine. For sorting: n² for the simple sorts, n log n for merge sort and heapsort, and no comparison sort can do better.

Thank you. Questions?

To conclude. Big O is an inequality that holds eventually, up to a constant. It captures asymptotic behaviour, and we can test it with limits. And because it ignores exactly the machine-dependent details, it's the standard language of algorithm efficiency.

That's why we can say merge sort beats bubble sort on any computer, for large enough inputs. Thank you, we're happy to take questions.

Why no comparison sort beats n log n

Any comparison sort is a binary decision tree: each comparison has two outcomes.
It must reach a different leaf for each of the n! orders, so it has ≥ n! leaves.
A binary tree of height h has at most 2h leaves: 2h ≥ n! ⇒ h ≥ log2(n!).
The largest n/2 factors of n! are each ≥ n/2, so n! ≥ (n/2)n/2.
log2(n!) ≥ (n/2)·log2(n/2) = Ω(n log n). ∎
The height h is the worst-case number of comparisons. Counting sort and radix sort escape the bound because they don't compare elements.

Use if asked why n log n is the limit. For 3 elements there are 3! = 6 orders, so at least 6 leaves, so height at least log₂6 ≈ 2.6, so 3 comparisons in the worst case.

Fine print worth knowing

The “=” only works one way

n = O(n²), but writing O(n²) = n is nonsense. Read it as f ∈ O(g): O(g) is a set of functions.

The limit test is sufficient, not necessary

f(n) = n(2 + sin n) ≤ 3n, so f = O(n). But f/n = 2 + sin n keeps oscillating and has no limit. The definition still works; use lim sup when the limit doesn't exist.

Log base doesn't matter

logan = logbnlogba

Changing base multiplies by a constant, so O(log2n) = O(log10n).

Big O is not “worst case”

Best, average and worst case are three different functions of n. O, Ω and Θ are bounds you can put on any of them.

Use for tricky questions about notation, missing limits, logarithm bases, or "is Big O the worst case?".

When the hidden constants do matter

Big O compares growth, not speed at a particular n. For small inputs a quadratic algorithm with tiny constants can win.

That's why real libraries are hybrids: Timsort (Python, Java) and introsort (C++ std::sort) hand small pieces to insertion sort.

Quicksort's n² worst case is avoided with random pivots (expected n log n), and introsort switches to heapsort if recursion gets too deep.

A short history

1894 Paul Bachmann introduces O, for Ordnung (order).

1909 Edmund Landau adds little o.

1976 Donald Knuth popularises O, Ω and Θ in computer science.
